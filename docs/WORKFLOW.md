# 협업 WORKFLOW — 사용자 / Claude 개발팀 / Codex

> 이 문서는 Ddooby 프로젝트에 적용하는 **협업 절차 초안**이다. 태스크마다 `../SPEC.md`, `PLAN.md`, `TASKS.md`의 실제 요구를 우선한다.
> 2026-11-11 현재 문서 GitHub 반영 미실시, Tracker Android 실기기 테스트 미실시.

## 1. 작업 모드와 승인 경계

| 상황 | 책임 | 주의 |
|---|---|---|
| 제품 요구/범위 결정 | 사용자 최종 승인 + Claude 메인 정리 | 제안은 승인과 구분 |
| 설계/계획/태스크 | Claude 메인 | `SPEC > PLAN > TASKS` |
| 구현/테스트/화면 연결 | claude-1 / claude-2 | 서로 같은 파일 동시 수정 금지 |
| 경계 조건 테스트 설계 | 요청 시 Codex | 검증 항목만 제공, 테스트 코드 구현은 개발팀 |
| 반복 오류 원인 분석 | 요청 시 Codex | 지정 로그·파일만 조사 |
| 핵심 경로 독립 리뷰 | 요청 시 Codex | 읽기 전용, main 반영 전 |
| 화면/에셋 원본 | 요청 시 Codex 디자이너 | 최종 시안은 사용자가 선택 |

Codex는 상주 개발자/PM이 아니다. **한 요청에는 한 역할만** 맡는다. 권한 경계는 `../AGENTS.md`를 따른다.

## 2. 요청 접수 → 기술 계획

1. Claude 메인이 무엇을/왜, 사용 흐름, 경계 조건, 수용 기준을 사용자와 정리한다.
2. 제품 결정은 사용자가 한다. 미정은 SPEC의 `확인 필요`로 남기며 사용자가 승인하기 전 확정 처리하지 않는다.
3. 변경 시 SPEC → PLAN(수정 파일·데이터 흐름·검증) → TASKS(태스크·의존성·담당·완료 기준) 순으로 반영한다.
4. 기존 저장소의 `AGENTS.md`, `CLAUDE.md`, 실제 코드·스크립트를 읽고 프로젝트 초안과 충돌하는 규칙을 정리한다.

## 3. 구현 브랜치·worktree

- main 폴더는 통합 상태로 두며, 구현 탭은 **별도 worktree**와 `feat/<태스크ID>-<요약>` 브랜치에서 작업한다.
- 포트는 현재 점유 상태를 보고 메인이 지정한다. 사용자 개발 서버를 임의 종료하지 않는다.
- 시작점은 `origin/main` 최신 상태를 확인하고 고정한다. 사용자/메인에게 임의로 원격 변경하지 않는다.
- 태스크 단위 커밋은 `[feat] <태스크ID> 설명`, 필요 시 `[fix]` 등의 형식을 따른다.
- 구현 탭은 테스트·build 결과와 커밋 해시를 메인에 보내고, **메인의 검토/승인 전 main 반영 금지**.
- 메인 승인 후 지정 구현 탭이 `fetch → rebase → 검증 → HEAD:main push`를 수행하도록 지시할 수 있다. 이 절차는 실제 프로젝트 작업 승인이 있을 때만 적용하며 **이번 초안 작성에서 실행하지 않는다**.

## 4. 구현 탭 지시서 필수 내용

- 한 줄 요약, **태스크 ID**, `SPEC`/`PLAN` 절, 기준 커밋·브랜치·작업 폴더.
- 수정 대상 파일/인터페이스, 책임과 금지 작업, 다른 탭의 파일 소유권, 필요한 설계 결정.
- `lint/typecheck/test/build` 중 실제 존재하는 검증 명령과 Android 화면/실기기 체크.
- 테스트 추가 항목, 완료 기준, 결과 보고(커밋·테스트 수·오류·캡처·실기기 판정).
- 메시지를 실제로 다른 탭에 보내지 못했으면 **위임했다고 하지 않는다**. 사용자가 옮길 수 있는 자기완결형 지시문을 제공한다.

## 5. 검증·리뷰·반영

1. 구현 탭이 결과/해시와 자동 테스트를 보고한다.
2. Claude 메인이 diff를 SPEC 기준과 대조하고 화면/현장 증거를 구분한다.
3. Codex 독립 리뷰 조건에 해당하면 해당 커밋을 기준으로 읽기 전용 리뷰를 받는다.
4. 지적이 맞으면 수정 탭에 되돌리고 검증한다. 저위험 보류 사항은 이유·후속 태스크를 기록한다.
5. 리뷰는 최대 2회 재요청. 초과하면 사용자에게 보고한다.
6. 검증 완료 후 승인된 변경만 main 반영. 완료 TASKS 체크는 **증거 확보 후** 한다.
7. 최종 보고에 기능·명령/결과·실기기/사용자 증거·미확인 사항·다음 결정이 포함되어야 한다.

## 6. 품질 및 개인정보

- 핵심 경로는 위치/GPS, 시간/거리, 저장 호환, 순환 코스 도착 상태, 개인화 데이터 분리 등이다.
- 소스 검토는 실기기 검증을 대체하지 못한다. 권한·OS 상태·GPS 환경이 필요한 기준을 단위 테스트만으로 완료 처리하지 않는다.
- 개인 GPS 좌표/집·직장 동선, 실사용자 식별 정보, API 비밀 키를 공개 브랜치·리뷰 파일·스크린샷에 남기지 않는다.

## 7. 모델·역할 선택

- 복잡한 위치·도메인·안전 로직은 충분한 검토가 가능한 구현 탭에 맡기고, 단순 UI/문구 수정은 별도 검증을 갖춰 분배한다.
- 역할은 **Orca 탭 제목**으로 고정한다: `claude-main`(Claude 메인), `claude-1`·`claude-2`(구현), `codex-main`(Codex 테스트 전략·트리아지·리뷰), `codex-design`(Codex 디자이너). 탭 ID와 터미널 핸들은 PC·세션마다 달라지므로 문서에 적지 않고 사용자에게 묻지도 않는다.
- 다른 탭에 메시지를 보내기 전에 아래 명령으로 탭 제목 → 핸들을 조회한다. `visualLayouts`의 탭 `title`로 찾고, `terminals[].title`은 실행 중인 프로그램이 바꾸므로 기준으로 쓰지 않는다.
  ```text
  orca terminal list --worktree current --include-visual-layouts --json
  ```
- 해당 제목의 탭이 없거나 둘 이상이면 추측하지 않고 사용자에게 보고한다.
- 모델, 작업 포트는 세션마다 확인한다. 지시문만으로 다른 탭의 모델/권한이 바뀌었다고 가정하지 않는다.

## 8. Codex 투입 기준 및 요청서

### 8.1 언제 투입하는가

| 상황 | 역할 | 시점 |
|---|---|---|
| 규칙·경계 조건·수용 기준이 복잡함 | 테스트 전략 설계자 | 구현 전 |
| 빌드/런타임 실패 반복 또는 원인 불명 | 실패 분석·트리아지 | Claude 메인 1차 확인 후 |
| GPS·보안·시간·저장·도착 판정·개인화 등 회귀 영향 큼 | 독립 리뷰어 | 구현 커밋 후, main 반영 전 |
| 신규 화면 또는 시각 에셋 | 디자이너 | 사용자가 시안 선택하기 전 |

단순 문구/작은 값 변경처럼 위험이 작은 작업은 자체 검증 가능하며 Codex 리뷰를 생략한 이유를 TASKS나 보고에 남긴다.

### 8.2 공통 요청서

요청서에 **한 역할, 태스크 ID, 기준/대상 커밋·브랜치, 지정 파일, 필요한 SPEC/PLAN 절, 테스트·증거, 금지 작업, 결과 파일 경로**를 포함한다. 저장소 전체/이전 대화를 요구하지 않는다.

요청서 문구 예시: `AGENTS.md와 docs/WORKFLOW.md 8절을 따른다. 요청된 결과 파일 외 수정, 커밋, push, 원격 변경은 금지한다.`

### 8.3 테스트 전략 결과

- 경계 조건, 실패 시나리오, 검증 항목과 각 기대 결과, 단위/통합/Android 실기기 등 확인 방법, 우선순위.
- 결과 첫 줄 `제안`, 경로 `.codex-out/<태스크ID>-test-plan.md`.
- Codex는 테스트 코드를 작성하지 않는다. Claude 메인이 채택한 항목을 구현 탭 지시문에 포함한다.

### 8.4 독립 리뷰 결과

- 지정된 `기준...대상` diff만 보며 정답성·보안·회귀·완료 기준·테스트 누락을 검토한다.
- 결과 첫 줄 `통과` 또는 `지적 있음`. 지적별 **높음/중간/낮음, 파일:줄, 재현 조건, 사용자 영향, 수정안**.
- `.codex-out/<태스크ID>-review.md`에 작성. 재리뷰는 동일 파일 끝에 `## 재리뷰 1`, `## 재리뷰 2`로 덧붙인다.
- 메인이 지적의 진위를 확인한다. Codex의 메시지는 사용자 제품 승인으로 보지 않는다.

### 8.5 실패 분석 결과

- 실패 명령/로그 원문, 환경, 커밋, 관련 파일만 확인한다.
- 가설별 근거/반증 및 다음 최소 확인 절차. 범위 밖 조사가 필요하면 범위와 이유를 보고하고 멈춘다.
- 결과 첫 줄 `원인 추정` 또는 `추가 조사 필요`; `.codex-out/<태스크ID>-triage.md`.

### 8.6 디자인 결과

- 요청서: 사용처, 크기(px)/비율, 색상·테마, 투명 배경, 기존 디자인/에셋 규칙, 타사 브랜드 모방 금지.
- 원본: `assets/<용도>-src/`; 목록/프롬프트 요약/날짜: `.codex-out/<태스크ID>-image.md`.
- 사용자가 시안 결정 → Claude 메인이 구현 탭에 연결 지시 → 구현 탭은 `CREDITS.md`에 `Codex(OpenAI) 생성, 날짜, 프롬프트 요약` 등 출처 기재.
- 고르지 않은 후보는 제품 저장소에 포함하지 않는다.

### 8.7 메시지 송수신

- 실제 전송·수락·결과를 확인하기 전에는 '위임 완료'로 보고하지 않는다.
- 구현 탭 worktree/브랜치와 사용자의 실행 중인 개발 서버를 변경하지 않는다.
- 과거 요청과 무관한 Codex 작업은 새 대화에서 요청해 맥락을 제한한다.

### 8.8 범위·비용 통제

- 리뷰는 한 태스크의 커밋 diff 단위로 좁히고, 디자인 후보는 한 번에 2~4개 정도로 제한한다.
- 승인되지 않은 외부 API 호출, 서버 배포, GitHub push는 수행하지 않는다.
