# Ddooby Navigator — PLAN

> 기술 설계 **제안 초안**. `../SPEC.md`가 요구사항의 최우선 기준이다.
> 상태: Navigator 첫 MVP 구현 전. Tracker 현장 검증 및 전환 승인 전.

## 1. 기술 스택과 기존 자산 (재확인 필요)

| 영역 | 이전 저장소 README에서 확인된 기술 | 선택 근거 / 대안 |
|---|---|---|
| 앱 | React Native + Expo, JavaScript, Android 우선 | Tracker와 유사한 기반 유지. 현재 의존성·native module 확인 필요 |
| 지도 | `react-native-maps`, Google Maps Provider | 기존 화면 재사용 후보. 다른 지도 공급자 비교는 실제 국내 품질·비용 확인 후 |
| 위치 | `expo-location` | Tracker 검증 결과의 **동작·테스트 기준**을 재사용; 코드를 무검증 복사하지 않음 |
| 길찾기/장소 | Google Directions walking, Places (과거 README) | MVP는 실측 고정 코스. API 사용 범위·국내 도보 품질·호출 비용 확인 |
| 화면 전환 | `@react-navigation/native`, native-stack (과거 README) | 기존 앱 구조 우선 |
| 테스트·배포 | 기존 package scripts, Android 개발 빌드 | 실제 `package.json`과 빌드 설정에서 확인 |

**표의 라이브러리 이름은 과거 대화 기준이지 오늘의 설치/작동 검증 결과가 아니다.** 신규 프레임워크로 전면 교체하지 않는다.

## 2. 의존 구조 (제안)

```text
screens/ (시간선택/미리보기/안내/요약)
  → application/ (산책 세션, 예상시간, 도착 상태)
  → domain/ (순환 코스, 시간 추정, 진행도, 품질 규칙)
  → services/ (위치 센서, 지도 공급자, 로컬 저장)
```

- `domain` 규칙은 화면과 지도 SDK에 의존하지 않도록 분리한다.
- 산책 상태는 `idle → preview → active → completed | cancelled` 같은 명시적 상태로 관리한다. 출발 직후 near-start만으로 `completed`가 되지 않도록 한다.
- 코스 정의는 화면 로직과 분리하고 검증 날짜, 기준 소요시간, 거리, 출발지/도착지, 주요 경유점을 기록한다. 실제 데이터는 현장 확인 후 추가한다.

## 3. 데이터 흐름

```text
사용자 시간 선택 (15/30분)
  → 해당 출발지의 검증 코스 조회
  → 기본 속도 + 보수적 정지 여유로 소요시간 추정
  → 미리보기 / 산책 시작
  → GPS 위치 품질 필터 → 경로 진행도·복귀 예상·도착 상태
  → 산책 종료 및 총시간·오차 저장
  → 이후 별도 산책 데이터로 개인화 예측 성능 비교
```

GPS 오차가 커지면 강제로 도착 판정하거나 정밀한 남은 시간을 확언하지 않고 '위치 정확도 낮음' 상태와 재시도를 제공한다. 취소/중단과 정상 완료를 별도로 저장한다.

## 4. 선행 및 태스크별 설계

### 4.1 NAV-00 — Tracker 인계 게이트

- `Ddooby/ddooby-tracker`의 `SPEC.md` 전환 기준, `docs/TASKS.md` 현장 6회 표, 검증 커밋, 품질·거리·시간 정의, 사용자 승인을 확인한다.
- 검증된 계산을 그대로 가져올지 모듈화해 옮길지 **실제 API/의존성 대조 후** 선택한다.
- Tracker 통과 전에는 개념 설계·문서 검토는 가능하지만, 첫 MVP의 위치 신뢰성을 검증 완료로 표시하지 않는다.

### 4.2 NAV-01 — 고정 코스 안내

- 회사 주변 실측 출발지 1곳에 대해 평지 15분·30분 코스를 준비한다.
- 코스의 경유 지점과 소요시간은 Tracker 기록 또는 현장 측정으로 검증한다. 검증되지 않은 코스는 '추천 완료'로 취급하지 않는다.
- 시작 → 코스 미리보기 → 위치 표시 → 복귀 화면 흐름. 경로 API에 과도하게 종속되지 않도록 고정 코스 데이터와 지도를 분리한다.

### 4.3 NAV-02 — 예상시간 및 순환 도착 판정

- 출발 당시 예상시간과 실제 산책 총시간을 모두 보존하고 사후 오차/시간 초과를 계산한다.
- 순환 경로에서는 출발 지점 반경만으로 완료 판정하지 않는다. **출발 후 최소 진행 상태 + 유효한 코스 진행도 + 최종 복귀 구간 진입** 등 조건을 명시하고 여러 경로 형태에 테스트한다.
- 임계값(예: 도착 반경, 진행도 비율)은 과거 README 값을 그대로 재사용하지 않고 실제 실측으로 결정한다.
- 위치 공백·이탈·정지·중도 종료에도 상태 전이가 일관되는지 확인한다.

### 4.4 NAV-03 — 개인화의 효과 검증

- 이전 유효 산책 기록으로 보행 속도를 산정하되 정지/공백을 분리한다.
- **평가 대상 회차를 학습 데이터에 섞지 않는다.** 동일 후속 산책에 기본속도 모델과 개인속도 모델의 예상시간을 각각 적용한다.
- 비교 지표: 복귀 소요시간 절대 오차, 실제보다 과소 추정한 횟수, 표본 수. 15분 점심 사용자는 늦은 복귀를 더 민감하게 본다.
- 표본이 충분하지 않거나 개선이 없으면 자동 개인화 적용을 보류한다. 적용 기준 수치는 실험 계획에서 확정한다.

### 4.5 NAV-04 — 리뷰와 다음 단계 결정

- Codex는 GPS 회귀, 순환 코스 조기 도착, 예상시간 과소, 데이터 누수, 안전한 fallback을 읽기 전용으로 검토한다.
- Claude 메인이 수용 기준과 지적 수정·검증을 관리한다. 사용자에게 반복 사용·시간 예측 결과를 보고한 뒤 테마/주말/목적지 범위 선택을 요청한다.

## 5. 검증

| 수준 | 테스트 | 확인 내용 |
|---|---|---|
| 단위 | 경로 진행·완료 상태, 시간 산정, 학습/평가 분리 | 출발 직후, 중간 출발지 통과, 0거리, GPS 튐, 중단, 첫 사용자 |
| 통합 | 코스 조회→시작→GPS→완료→저장 | 완료/취소 구분, 앱 재시작 후 이력 정확성 |
| Android 실기기 | 15/30분 평지 검증 코스 | 안내, 복귀 시각, 과소 추정, 조기 완료 여부 |
| 사용자 관찰 | 다른 날 자발적 재시작 | 반복 사용 여부를 기록(아직 데이터 없음) |
| Codex 리뷰 | 변경 커밋과 해당 증거 | 회귀·완료 기준·누락 테스트 |

`npm` 스크립트/Expo 명령은 실 저장소에서 확인할 때까지 확정하지 않는다. 구현 탭은 lint/typecheck/test/build 중 실제 존재하는 명령을 실행하고 누락 명령은 미구축으로 보고한다.

## 6. 운영과 리스크

- 위치 이력 최소 수집/로컬 기본, 백그라운드 위치 권한·배터리 영향·GPS 정확도 명시.
- 도보 경로의 안전성과 신호 대기/경사는 지도 API가 보장하지 않을 수 있음. 실측 여부가 구분된 코스만 사용.
- Android 지도/장소/경로 API 요금 및 호출 제한은 실제 사용 전 확인. 비밀 키는 저장소에 넣지 않음.
- 초기 규모에서는 데이터 품질·반복 사용 검증이 먼저. 코스 운영비·업데이트 주체·수익 가설은 제품 검증 후 결정.

## 7. 확인 필요

- 실제 Navigator 저장소의 경로 구조·버전·검증 명령.
- 회사 주변 출발지와 15/30분 코스의 GPS/시간 데이터.
- 개인화 모델의 채택 기준, 순환 완료 판정 임계값.
- 제품 의사결정: 첫 MVP 고정 코스 범위와 향후 테마/목적지 우선순위.
